# BBR 与拥塞控制

当路上已经很堵，继续猛发数据可能让排队更长。拥塞控制就是发送端根据网络反馈调整发送节奏的办法。BBR 根据对瓶颈带宽和往返时间的估计来控制发送；它有不同版本和不同协议实现。[Google BBR 项目](https://github.com/google/bbr)

## 它能改变什么

| 问题 | BBR 是否直接解决 |
| --- | --- |
| TCP 在某条路径上的发送效率 | 可能改善，也可能没有明显收益，需要对照测量 |
| 住宅代理套餐限制为 50 Mbps | 不能把套餐上限变成 1 Gbps |
| 客户端密码错误、证书过期 | 不能修复 |
| Hysteria2 的 QUIC 拥塞控制 | Linux TCP 的开关不会直接替换 QUIC 自己的实现 |
| 目标网站拒绝账号或请求 | 不能保证通过 |

BBR 是算法，不是单独的“加速进程”。看到节点报错，不应先找一个不存在的 BBR 后台程序是否崩溃。

## 先看当前状态

以下命令在 **VPS 的 SSH 终端**运行，只读取设置：

```bash
uname -r
sysctl net.ipv4.tcp_congestion_control
sysctl net.ipv4.tcp_available_congestion_control
```

第一行查看内核版本；第二行查看默认 TCP 拥塞算法；第三行查看当前已注册的算法。列表里没看到某算法，也可能只是相应模块没有加载。进程还可能为单个连接选择算法，所以默认值不等于所有已有连接都在使用它。[Linux 内核参数说明](https://docs.kernel.org/networking/ip-sysctl.html)

若以后需要变更，先记录原值与同一路径的速度，再按该系统和内核的文档选择算法；变更后建立新连接对照，必要时恢复原值。本次教程改编没有在 tyccc 开启或更换 BBR，也没有声称测出了加速倍数。

视频里“输入某个菜单编号”只适用于那个版本；看到当前菜单中的功能名称再操作。是否需要重启取决于是否更换内核及具体改动，不能把“启用 BBR 一律重启整机”作为通用步骤。配合 [[带宽流量延迟与丢包]] 阅读。
