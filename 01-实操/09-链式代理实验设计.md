# 09 · 链式代理实验设计

> [!NOTE]
> 本课是基于官方配置模型整理的进阶实验设计，尚未在 meu 或 tyccc 执行。没有接入住宅资源，也没有公网 SOCKS 出站实测。先完成 [[06-连接验证与结果]]，再按本课规划独立测试；原有截图不能作为本课成功的证据。

## 这次要证明什么

证明“某一个测试入口的请求，经中转交给指定落地，再由落地访问目标”。成功标准是实际请求的路径和出口符合预期，而不是面板上多了一个出站。

```mermaid
flowchart LR
  A[测试客户端] --> B[中转：测试入站]
  B --> C[路由：匹配测试标签]
  C --> D[中转：落地出站]
  D --> E[落地服务]
  E --> F[查询出口的目标网站]
```

这是原理图，不是执行截图。基础概念见 [[链式代理与中转落地]]。

## 先准备一张私人参数表

| 参数 | 从哪里取得 | 写错会怎样 |
| --- | --- | --- |
| 中转服务器与可用测试入口 | 自己管理的 VPS 和已测试配置 | 客户端第一跳就失败 |
| 测试入站实际 tag | 面板生成的 Xray 配置或对应标签字段 | 路由匹配不到；备注不一定等于 tag |
| 落地地址、端口 | 自有落地配置或供应商交付信息 | 中转找不到下一站 |
| 落地协议及凭据 | 与落地服务端一致 | 握手或认证失败 |
| 保护中转到落地的方式 | 双方支持的加密传输配置 | 不能只凭第一跳已加密来判断第二跳 |
| 预期出口与对照出口 | 落地说明和实际请求核对 | 无法区分是否绕过了链路 |

使用自己的真实值填写私人记录，不能复制教程里的标签就认为已经对应现有入口。先保存备份，给测试入口和客户端使用独立身份；不要把已有六条入口全部选入新规则。

## 方案 A：中转连接一个代理端口

在 3x-ui 的“出站”相关页面创建 SOCKS 出站，填写下一跳地址、端口和供应商要求的认证信息，设置一个可辨认的标签，例如 `residential-test-out`。标签只是名字，即便这样命名，也不代表验证了住宅属性。

关键核对：这是**出站**，不是把一个无认证 SOCKS **入站**开放给公网。标准 SOCKS 不提供传输加密；先确认对接方式能保护公网这一段。未确认之前，本课只做参数设计，不建议拿裸 SOCKS 作为默认教学部署。[SOCKS 出站字段](https://xtls.github.io/config/outbounds/socks.html)

不同版本的面板可能使用表单或 JSON 编辑器，配置字段也可能迁移。不要把网上旧版的 `servers` 数组与当前的扁平字段混合粘贴；对照正在运行的核心版本与面板生成结果。

## 方案 B：中转连接另一台自己管理的 VPS

先在落地 VPS 准备一个独立、已验证的加密入站，再在中转创建匹配的出站。例如使用 Shadowsocks 时，双方的算法、服务器与用户密钥安排要匹配，SS2022 多用户配置尤其不能只填一段普通密码。可先复习 [[Shadowsocks-2022配置]]；出站字段以 [Xray Shadowsocks 出站说明](https://xtls.github.io/config/outbounds/shadowsocks.html) 为依据。

这只是可选架构，不代表 Shadowsocks 必然比 TLS 或 REALITY 快，也不要求必须选它。普通 VPS 到普通 VPS 可以练习链式路由，但不能因此称为“住宅链路”。

## 将一个测试入口关联到落地出站

在路由页面新建规则：入站条件使用实际测试入站 tag，出口选择刚创建的出站 tag。下面只说明一条规则的结构，不是完整配置文件，也没有替换服务器现有规则：

```json
{
  "type": "field",
  "inboundTag": ["chain-test-in"],
  "outboundTag": "residential-test-out"
}
```

`inboundTag` 数组回答“哪些入口的请求”，`outboundTag` 回答“交给哪一个出口”。两个示例标签都必须对应真实配置中存在的对象。

规则从上到下匹配，命中第一条适用规则后采用其出口；若没有规则匹配，默认使用第一个出站。检查测试规则之前是否已有更宽的规则，同时保留原有必要限制。[路由匹配规则](https://xtls.github.io/config/routing.html)

按当前面板提示保存并应用到 Xray；查看成功提示、核心状态和日志。管理面板与 Xray 是两个角色，不能把“必须重启面板”当成所有路由修改的通用步骤。当前版本是否自动应用、是否还需重载，要以实际界面和结果确认。

## 做四组验收

| 对照 | 应观察到什么 | 能证明什么 |
| --- | --- | --- |
| 原来的独立入口 | 请求成功、原出口符合预期 | 第一跳和对照基础正常 |
| 新测试入口 | 请求成功、出口符合落地实际出口 | 请求至少到达了预期出口 |
| 查看测试规则及流量日志 | 测试请求命中相应入站和出站 | 补充路径证据，尤其两种方案出口相同时 |
| 仅使独立测试落地暂时不可用 | 测试请求失败，原入口仍可用 | 没有通过直连悄悄绕开故障 |

测试程序应显式指定待测客户端代理。只在普通浏览器里查一次 IP，可能受系统代理、浏览器代理、分流规则影响。若要求落地失败时不直连，先检查没有配置自动切换到直连的后备出口。

TCP 成功不代表 UDP、DNS 或每个应用都经过同一路径；分别用对应请求验证，并记录尚未验证的项目。速度对比见 [[带宽流量延迟与丢包]]。

## 排错与撤回

若还是原出口，先查 tag 是否匹配、规则顺序、客户端是否选了测试入口。若连接失败，依次查第一跳、落地可达性、认证、协议版本、DNS 和日志。不要把“端口不通”直接写成“IP 被封”。

撤回时禁用新测试规则并应用，再验证原入口；没有规则依赖后再清理测试出站与入口。保留测试前后的记录。只有局部配置无法恢复时，才评估 [[备份恢复与升级|恢复备份]]，因为整库恢复可能覆盖后来新增的数据。
